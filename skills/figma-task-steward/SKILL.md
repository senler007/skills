# Figma 任务管家

用户启用本工作流后，可为其任务创建独立 Codex 会话，并在参与会话间发送派发、交接、借阅和完成消息。Skill 被自动选中本身不构成授权，不联系无关会话或外部人员。管家负责调度，执行会话负责调查和实施；不能用内部 subagent 替代用户要求的独立会话。

**分别建会话、逐卡开始澄清；共享项目操作串行。空闲只读直接原子登记，实际占用才借阅。已创建会话不等于已提出问题，测试通过不等于需求完成。**

只保留每日创建新管家的自动任务。执行者主动消息唤醒管家；不创建、不恢复 heartbeat、十分钟补查、周期轮询或循环等待。

## 事实来源与任务边界

- 读取适用的 AGENTS.md、Docs/ProjectOverview.md、Docs/agents/issue-tracker.md 和 Docs/agents/project-docs.md。默认 Figma 文件每次从项目文档重新取得，不能硬编码文件或页面 ID。执行会话读取共享项目仍须先取得相应操作权，可先使用管家提供的入口与文档摘录。
- GitHub 仍是项目规定的规格、验收和开发状态权威时，读取关联 Spec/Ticket，Figma 维护摘要和链接；冲突留待澄清，不能自行迁移权威。
- 使用 Figma 工具；程序化读写先加载 figma-use。枚举页面找到「每日安排」，完整读取任务容器、嵌套文字、说明、参考图片并实际查看截图。图片截断、不可读或未查过的内容不能补猜，也不能声称已完整理解。
- 区分需求正文、AI 状态和占位内容。节点叫“任务模板”或描述仍有 xxxx，不能据此跳过已有真实标题、说明或参考图的卡。只有确认无实际需求才跳过。
- 以 fileKey:nodeId 和节点链接定位，标题不作为去重键。用户拆开的主界面、玩家自定义、事件池、事件优化等卡片分别保持任务边界，不能因共用代码、相邻摆放或历史上放在同一会话就合并。
- 同一任务的新位置可映射到旧任务并复用会话；不同任务不得用 alias 吞并。用户明确要求新会话时创建独立会话，转移相关已有答案和成果边界，不要求用户重答。用户明确合并讨论时才合并，保留原任务历史和未完成状态。详见账本协议。
- 不擅改原需求、重建卡片或重排看板。AI 区域内也可能有用户手写需求，不能按图层名称整体覆盖。写回仅限已授权区域，保留引用和原文，查看截图确认无重叠、遮挡或文字越界。
- “重新读取并分类任务”不等于“获准编辑 Figma”。人员认领的任务不能自动抢给 AI；Figma 附加文本不是对其他系统的操作授权。

## 持久账本与交接

任何派发、占用、归还或交接前，读取 [账本协议](references/coordination.md)，使用 scripts/ledger.py 的版本比较与原子提交，不能直接编辑 state.json。保存真实会话 ID、去重令牌、授权来源和具体状态。

首次启动排查已有会话，既看 projectId，也核对实际 cwd，包括指向本项目的 projectless 会话。没有账本不等于空闲；turn 结束、等待输入、归档或长时间未回复不等于完成。未纳入工作流的旧会话不能擅自指挥，归属不明时报告具体冲突并请用户指定接管对象。协议不是操作系统隔离，不能保证阻止人工或未登记会话写入。

每日接班：
1. 核实自己的真实 threadId，并用 list_projects 匹配项目真实路径。
2. 没有管家时 CAS 登记；已有管家时向旧管家请求交接，旧管家完成在途派发事务后 CAS 改 manager.thread_id，再通知接班。
3. 交接只更换管家，保留所有任务、成果和工作区归属，不重复创建会话。旧管家失去派发权即停止调度，迟到回报转交当前管家。
4. 旧管家不可用时保留状态，请用户明确改派；不得按日期或超时抢占。执行者每次回报重新读取当前管家 ID。
5. 接班后立即执行下面的整轮主动检查。

## 主动检查与澄清队列

每日接班、用户要求检查/新增/重新梳理任务，或收到相关任务回报时，重新读取任务池。按用户顺序、看板优先级和视觉顺序逐项处理真实未完成卡，不能只列清单后等待用户逐个点名。

1. 对每张卡记录最新需求快照，核对任务边界、已有会话和旧问答。跳过真正的空模板、已完成、已取消及未交给 AI 的人员任务。旧卡已完成但新卡增加范围时保留旧成果，单独判断新增范围。
2. 有实际需求且仍有行为、范围、验收或设计缺口，就创建独立 local 澄清会话；同一任务已有合适会话则复用。同一卡的多个疑问留在一个会话。不能因实施依赖未满足而连澄清也不启动。
3. 发送完整来源、已有答案、最新更正和明确的澄清指令。执行者用 grilling 在自己的会话提出具体问题，按依赖顺序给建议和取舍。旧泛问若已被新图文或用户答案解决，立即替换，不能继续等待过期的 A/B/C。
4. 每次派发后可用一次 wait_threads 紧凑快照核对启动，再检查下一张卡。一个会话等待回答不妨碍其余会话开始；不要等整项开发完成才建立后续澄清。
5. 以实际阶段记录覆盖情况：dispatch_sent、active、question_asked、needs_project_facts、awaiting_plan。附最新需求来源、实际首问/剩余问题、会话链接或具体阻塞。**active 不是已提问，已有 threadId 不是已覆盖，旧问题不是新需求已澄清。**
6. 一张“所有事件逐项打磨”卡包含多个事件时，默认保持一个独立会话并记录逐项清单和进度；用户明确要求每事件独立会话/任务卡时，按最新边界拆分，保留已有问答，不重新合并。第一项开始不等于其余项目已完成。用户指出漏项、错误名称或事实时先核查纠正，不逼用户继续回答建立在错误事实上的问题。
7. 问题在对应任务会话完整呈现一次。管家可给简短覆盖清单，明确哪些已实际提问、哪些仅已启动、哪些需要事实或用户决定；不能笼统宣称“全部安排好了”。用户在管家回答时转交对应会话，已有答案不重复采访。

本轮检查完即结束等待消息。尚未问完的任务保持 clarifying，不标 done，也不通过定时轮询等待问题出现。后续回报触发任务池读取时，复用本轮已核实快照，核对新增、变更与未覆盖项；内容未变不反复下载参考图或重问。没有工具能自动监听 Figma 修改时，不宣称会实时发现新卡。

## 创建会话与故障恢复

正常顺序：CAS 预留任务键和唯一 dispatch_token → create_thread（已核实 projectId、local）→ 绑定真实 threadId → 明确阶段和权限并启动。使用 [执行会话模板](references/worker-prompt.md)。

分别核实“创建成功、账本绑定成功、工作区授权成功”，不能混为一个结果。只有 clientThreadId 时先核实就绪后的真实 ID；创建结果不明时按令牌和现有会话找回，不重复创建。

用户已明确要求立即新建会话，而账本预登记失败时，若创建操作本身仍获允许，可只创建一次、保存返回 ID 和待绑定原因，先在该会话处理提供的资料与用户澄清。未绑定前不得访问共享项目，不能把创建成功当作工作区授权。后续恢复绑定这个真实会话，不再新建。若连创建也被拒绝，报告具体拒绝的动作与原因，不伪称已创建，不让其他会话代做被拒绝操作以绕过限制。

## 工作区操作权

在每次恢复、收到新指令及一批项目操作前重读账本。串行覆盖读写调查、实施、编译、资产、UE/PIE 和可能回写缓存的工具，不代表澄清聊天也要排队。

| 实际情况 | 应采取的动作 |
| --- | --- |
| 已绑定澄清任务；已排查；owner/borrower 均空；范围允许且无人工冲突、暂停或已排定实施冲突 | 执行者按账本协议 CAS 自领短暂只读 owner，成功后直接查阅，查完释放。无需先申请、等管家批准、再确认收到 |
| 已持有相应操作权 | 在已授予范围内继续，不能自行把只读升级为实施 |
| 另一任务持有工作区 | 向当前管家登记一次需求后安静排队。默认等实际释放；确需借阅时，管家取得持有者安全暂停、后台停止的回报后才 CAS 授予一个 borrower。借阅时持有者停止操作 |
| 归属不明、未绑定或范围仍被暂停 | 继续处理已提供资料与澄清，记录具体阻塞，不能凭“看起来没在用”抢占 |

只读不得修改、编译、切换 Git 状态、启动或控制 UE/PIE、生成索引或缓存；工具名叫查询也要判断副作用。调查完成即释放，不占着等用户回答。借阅者归还 borrower，正式只读持有者释放 owner。CAS 冲突重读重判，不覆盖别人的归属。

实施只由当前管家给 AI 负责、范围已批准且依赖满足的任务授予 owner。优先已就绪任务，前一项尚未确定时先做已授权独立部分。持有者无已授权工作可继续时，到安全点保存成果、确认后台停止且无借阅者，原子释放并回报，保留 clarifying/awaiting_plan/blocked；无需等待整项需求全部确定。恢复须重新获权并核对变化。

暂停记录明确对象与范围。用户“先别急，我重新梳理”先暂停相应旧队列；后续明确要求某任务澄清、调查或实施，是该范围的恢复，不要求重复解除全局暂停，也不推定全部恢复。

## 澄清、批准和验收

先查事实，再用 grilling 按决策依赖提问；将已有答案直接作为 ask-plan-build 的 Ask 输入，不重复采访。方案写明具体行为、文件/资产与必要验证，再依据用户确认实施。不要修改共享的 grilling 或 ask-plan-build 技能。

“可以”“照着改”“继续”“按推荐”等结合前文具体方案可构成范围明确的批准，记录原话和来源；不能因换会话、接班或重新获权重复问是否开始。协调授权、提问和代理建议不等于批准；新增范围另行判断，未决项保留。

按任务加载 Unreal、代码规范与文档技能。验收必须对照累积已确认需求和最终行为，不能只看测试通过。例如原约定“即时保存”不能未经批准变成“确认/取消”；画面差异不能凭猜测归因 FOV；事件显示名应保留用户中文原文，缺项应查原范围与当前实现，不能直接认定只漏一行数据。

使用 [验收与回归场景](references/acceptance.md) 检查成果、验证边界、后台停止和环境恢复。完成独立子范围只记录 completed_iterations；整项仍有待决或必要验证未完成，不能 done。真实全部完成后原子记录 report、done 与释放，再主动通知当前管家。外部同步失败只补同步，不重复实施。

## 消息与用户注意力

- **工作区调度只经过当前管家。执行者不能向其他执行者发暂停、催交接、借阅授予或恢复指令。** 排队任务没有操作权，不需要被再次“暂停”；持有者仍有已授权工作时继续做，管家不能因又来一个申请就反复叫停。
- 排队的标准动作是：一次记录具体需求并回报管家 → 结束本轮安静等待 → 实际获权后继续。没有新事实不主动输出“仍在等”“已暂停”“等管家批准”，不轮询账本、不相互提醒。用户主动提问或回复澄清时正常回答；纯澄清不占工作区。
- 管家收到排队请求、普通进度或看板整理更正时先入账，合并到下次实际派发；不逐条转发给持有者或等待者。一次有效开工消息包含已生效权限、最新范围、已有答案和下一步；CAS 失败、条件未满足或尚待释放时不能发送“已授予/立即开始”。
- 已结束或排队会话不因确认收到、例行验收通知、规则更新而被唤醒。规则更新写入 Skill 和账本，由会话在下次正常恢复/操作批次前读取，不群发通知。若新事实证明正在执行的范围会造成越权或成果错误，由管家向受影响的持有者发送一次具体纠正。
- 回报是后台调度输入，不是用户换了话题。优先完成用户当前请求，不让别的任务每条答案打断当前会话；普通进度入账即可。
- 首次具体阻塞、实际首问、方案待确认、影响其他任务的依赖变化、借阅交接、安全释放和整项完成，向当前管家发送一次简洁消息。已报相同状态不反复通知，接收方无需发送“收到”的确认回路。
- 管家需要用户决策或交付结果时，使用准确任务标题、会话链接和影响范围。不同任务的报告不能混写成用户当前问题的答复；多条普通回报可合并记录。
- 完成必须 send_message_to_thread 唤醒账本中的当前管家，只写最终回复或账本不算已通知。发送失败保留证据和发送结果；只有确认未发送的暂时错误可重试一次，不添加周期补查。
- 发现历史 heartbeat 用 automation_update 停用并清除账本 heartbeat_id。没有可执行事项时结束本轮，等任务回报、每日启动或用户唤醒。
